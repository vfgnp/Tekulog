# 探索マップ作り直し + カレンダータブ移動 — 要件定義書

- 対象バージョン: v1.2.0 の次(バージョン番号はリリース時に別途決定)
- 作成日: 2026-09-30
- 関連: `02-basic-design.md`(基本設計)/ `03-detailed-design.md`(詳細設計)

## 1. 背景と目的

### 1.1 仕様変更
カレンダーは現在、ホーム画面右上のアイコンからしか開けない。これをタブバーの
「ホーム」と「探索マップ」の間に移し、常に1タップで開けるようにする。

### 1.2 不具合
探索マップで地図を拡大・縮小・移動すると、歩いた範囲を示す印(フォグの晴れた部分。
以下「晴れ」)が地図とズレる。現行実装(`Tekulog/Views/ExploreMapView.swift`、
コミット `8523945` 時点)の調査で、以下5つの原因を特定した。

| # | 原因 | 該当箇所(現行) | 利用者から見える症状 |
|---|---|---|---|
| A | フォグは地図の上に重ねた SwiftUI `Canvas` で、`fogPoints` が変わった時しか再描画されない | `fogOverlay(proxy:)` | 操作中、晴れが画面に貼り付いたまま地図だけ動く |
| B | カメラ変更の通知は操作終了時(`.onEnd`)のみ。さらに前回取得領域との重なりが75%超だと再取得せず `fogPoints` が変わらないため、再描画自体が起きない | `refreshFogIfNeeded(region:)` | 少し動かして指を離しても、晴れがズレた位置に残り続ける |
| C | 晴れの半径が画面上 46pt 固定 | `fogOverlay(proxy:)` の `radius` | 拡大しても晴れが大きくならない/縮小すると実際より広く晴れて見える(初期表示の縮尺では半径約300〜400m相当。画面寸法による) |
| D | 重なり率を「小さい方の span」で割るため、ズームアウトすると常に 1.0 になり再取得されない | `overlapRatio(_:_:)` | 縮小したとき、および縮小後に旧領域を含む範囲で動かしたとき、新しく画面に入った範囲の晴れが表示されない |
| E | グリッドの経度セル幅を「点そのものの緯度」で計算している。経度方向のセル境界が緯度行(75m幅)の中で連続的に動き、南端と北端で約1.4セル分(東京付近)ずれる | `ExplorationService.bucket(for:)` | 下記 |

原因 E の具体的な影響(同じ点は常に同じセルになるので「二重登録」は起きない。問題はセルの形と中心の不安定さ):

- セルが正方形にならず、東西に大きく傾いた細い帯になる。通過セル数が進行方向で変わり(経路点が 8m 間隔の場合の試算で、3km 直進すると南北方向は約90セル、北東方向は約40セル。正方格子ならそれぞれ40、57)、
  「新エリア数」「開拓率」が移動方向によって過大にも過小にもなる。
- 保存されるセル中心の経度が「最初にそのセルへ入った点の緯度」に依存し、セルごとに一意に決まらない。
- 未開拓方向の判定は保存済みの中心を再びセル番号に変換して使うが、その約3割が元と違うセルになる。このため未開拓方向の提案が誤る。

操作中の完全な追従(A)とピッチ表示への対応は、地図に別ビューを重ねて描く方式では保証できない
(重ねた描画は地図の描画と同じフレームに同期しない)。B〜D は個別に直せるが、A を解消する方式に変えれば不要になる。
E は表示以前にデータの定義が不安定である。よって方式から作り直す。

### 1.3 目的
- 晴れが地図に対して常に正しい位置・正しい大きさで表示されること
  (広域表示での視認性確保のための例外は FR-4 に定める)。
- 探索データ(開拓済みセル・開拓率・新エリア数・未開拓方向の提案)が、安定した一意なグリッドの上で互いに矛盾しないこと。
- カレンダーへタブから直接行けること。

## 2. 用語

| 用語 | 意味 |
|---|---|
| フォグ | 探索マップ全体を覆う半透明の暗い層。未開拓を表す |
| 晴れ | フォグが抜けて地図が見える部分。開拓済みを表す |
| セル | 探索グリッドの1マス(一辺 75m、`Tunables.explorationCellSizeMeters`)。Core Data の `ExploredCell` 1行に対応 |
| 開拓率 | 自宅から半径 1,500m(`Tunables.explorationRateRadiusMeters`)以内の開拓済みセルの割合 |
| 新エリア数 | 1回の外出で新しく開拓したセル数(`WalkSession.exploredNewCellCount`) |
| フロンティア | 自宅から見て未開拓の方向・地点の提案(「まだ歩いていないエリア」) |
| 再構築 | 既存の開拓済みセルを破棄し、保存済みの外出の経路から作り直す処理(FR-6) |

## 3. 機能要件

### FR-1 タブ構成
- FR-1.1 ボトムタブバーは左から **ホーム / カレンダー / 探索マップ / マイページ** の4つとする。
- FR-1.2 カレンダータブは既存の `CalendarView`(月グリッド+最近の記録、日タップ→その日のルート、行タップ→セッション詳細)をそのまま表示する。
- FR-1.3 ホーム画面右上のカレンダーアイコン(従来の導線)は削除する。
- FR-1.4 DEBUG 用起動引数 `-initialTab N` は新しい並びに従う(0=ホーム, 1=カレンダー, 2=探索マップ, 3=マイページ)。

### FR-2 フォグの地理固定
- FR-2.1 晴れは地図上の地理座標に固定され、パン・ピンチズーム・回転・ピッチ(傾き)の**操作中も操作後も**、地図(道路・建物)との相対位置がズレない。
- FR-2.2 フォグは自宅マーカー・フロンティアマーカーを隠さない(マーカーはフォグより手前)。

### FR-3 晴れの大きさ
- FR-3.1 1つの開拓済みセルが晴らす範囲を、セル中心からの**実寸距離**で次のように定める(値は `Tunables` で調整可能):
  - 中心から **75m まで**: 完全に晴れる(フォグなし)
  - **75m〜150m**: 外側へ向かって徐々にフォグの濃さへ戻る
  - **150m より外**: そのセルによる晴れはない

  オーナーの決定は「晴れる幅は実寸で半径約150m」。本書ではこれを「150m=ぼかしの外周、完全に晴れるのは内側 75m」と解釈した
  (見た目の晴れの半径は 110m 前後になる)。内側の割合は `Tunables` で調整でき、実機確認(AC-4)でオーナーが見た目の広さを確認して確定する。
- FR-3.2 晴れの大きさは地図の縮尺に連動する(拡大すれば大きく、縮小すれば小さく見える)。ただし FR-4.1 の下限に達した後は画面上の大きさを保つ。
- FR-3.3 複数のセルの晴れが重なる部分は継ぎ目なくつながって見える(地図の描画単位の境界で線や段差が出ない)。

### FR-4 広域表示での視認性(オーナー承認済みの例外)
- FR-4.1 地図を縮小して FR-3.1 の実寸が画面上で小さくなっても、1つの晴れは**画面上の半径 4pt**(`Tunables` で調整可能)を下回らない。
  下限に達した縮尺より広域では、視認性を優先して実寸より大きく描く。位置(中心)は FR-2.1 のとおり地理座標に固定のままとする。
  また広域表示では、描画負荷を抑えるために近接するセルをまとめて描いてよい。その場合も、元のセルの「完全に晴れる範囲」と「外周」は
  まとめた晴れに必ず含まれること(歩いた場所がフォグに戻って見えない・連続した経路が途切れて見えない。ぼかし部分の濃さの一致までは求めない)。
  (これらの拡大が効き始めるのは、東京付近でおよそ画面幅 13km 超の広域表示(実装工程での実測値)。初期表示(約 3km)を含め、それより狭い範囲では常に実寸どおり)

### FR-5 表示範囲に依存しない表示
- FR-5.1 画面に表示されている範囲内の開拓済みセルは、地図の位置・縮尺・それまでの操作履歴によらず、必ず晴れとして表示される。

### FR-6 グリッドの安定性と既存データの再構築
- FR-6.1 グリッドは次を満たす:
  - (a) セルは利用範囲(日本国内)でおおむね一辺 75m の矩形である(東西幅の誤差 ±1% 以内)。
  - (b) セル中心はセルごとに一意に決まる(どの点から入っても同じ値)。
  - (c) セル中心をセルに変換し直すと、元と同じセルになる。
- FR-6.2 セルの割り当ては自宅位置に依存しない(自宅を変更しても開拓済みデータは変わらない)。
- FR-6.3 本変更を含む版へ更新後、最初にアプリの画面を表示した起動で、既存の開拓済みセルを破棄し、保存済みの**確定済みの全外出**(分類済みか否かを問わない)の経路から新しいグリッドで再構築する。利用者の操作は不要。
  更新後の最初の起動が画面を伴わないバックグラウンド再起動だった場合は、次に画面を表示した起動で行えばよい。
- FR-6.4 再構築では各外出の「新エリア数」も古い順に計算し直す。
- FR-6.5 再構築は、分類済みの外出の**目的分類(手動で変更したものを含む)を変更しない**。未分類の外出(探索機能導入前の版から直接更新した場合など)は従来どおり自動分類する。
  開拓済みセルと各外出の新エリア数は、更新の経路(探索機能導入前の版からの更新、旧版の後追い処理が途中だった状態からの更新など)によらず同じ結果になる。
  未分類だった外出の目的分類は、再構築時点の自宅設定と履歴で自動判定する(更新の経路によって異なりうる)。
- FR-6.6 再構築が途中で中断されても(アプリ終了など)、次回起動時にやり直して最終的に正しい状態になる。
- FR-6.7 再構築の前・途中に新しい外出が確定しても、再構築完了時点の開拓済みセルと全外出の新エリア数は、「確定済みの全外出を開始時刻の古い順に1回ずつ反映した結果」と一致する(セルの重複も起きない)。
- FR-6.8 外出を削除しても、開拓済みセルと他の外出の新エリア数は変更しない(現行踏襲)。
- FR-6.9 再構築の実行中に探索マップを表示した場合は、更新中であることを画面に示し、完了した時点で表示中でも晴れ・開拓率・フロンティアを最新の状態に更新する。

### FR-7 既存機能の維持
- FR-7.1 自宅マーカーを表示する。
- FR-7.2 「自宅まわりの開拓率」ピルを表示する。開拓率は従来どおりセル(75m)単位で算出する。晴れの見た目(半径150m)はセルより広いため、
  見た目の晴れの広さと開拓率の数値は一致しない(仕様として許容する)。
- FR-7.3 「まだ歩いていないエリア」シート(近い順・最大5件・方位ラベル・自宅からの距離)を表示し、行をタップすると地図がその地点へアニメーション移動する。候補地点はマーカーでも表示する。
  候補地点は、地図上で晴れて見える範囲(いずれかの開拓済みセルの中心から 150m 以内)を避けて選ぶ(晴れた場所に「未踏エリア」のマーカーが立たないようにする)。
- FR-7.4 自宅未設定時は、自宅設定への導線(CTA)を表示する。
- FR-7.5 探索マップタブを表示するたびに、自宅を中心とした範囲(約 3km 四方)から始める(現行踏襲。タブを離れる前の表示位置は保持しない)。
- FR-7.6 ホーム画面の「探索ナッジカード」「新エリア」バッジ、セッション詳細の表示は、再構築後の値で引き続き機能する。

### FR-8 データの反映
- FR-8.1 外出が確定して開拓済みセルが増えたら、次に探索マップタブを表示した時点で晴れ・開拓率・フロンティアに反映される。
- FR-8.2 探索マップを表示している最中に外出が確定した場合の即時反映は必須としない(再構築完了時は FR-6.9 のとおり即時反映する)。

## 4. 非機能要件

- NFR-1 性能: 開拓済みセルが 50,000 件ある状態で、地図の描画単位1枚(256pt 四方・2倍解像度)あたりのフォグ描画時間が、最も負荷の高い縮尺でも平均 50ms 以内。
  計測環境は**開発機(Intel Mac)の iOS シミュレータ・最適化ありのビルド(Release 構成)の自動テスト**とする(実機 iPhone XR の代理指標。合否はこの環境の値で判定する)。
  最適化なし(Debug 構成)では描画の計算が数十倍遅くなり出荷するビルドの実態を表さないため、Debug では計測値を記録するだけで判定しない。
  あわせて実機で、DEBUG 用起動引数により合成した 50,000 セルを**メモリ上だけ**で描画に渡し(Core Data には書かず、利用者の実データを変更しない)、操作時に引っかかりがないことを目視確認する。
- NFR-2 プライバシー: 外部送信を追加しない。地図タイルと逆ジオコーディング(フロンティア地名)は従来どおり Apple のサービスのみ。App Store のプライバシー表示「データを収集しません」を維持する。新たな権限要求を追加しない。
- NFR-3 並行性: Swift 6 strict concurrency に準拠し、コンパイル警告・実行時の isolation 違反(`dispatch_assert_queue_fail`)を出さない。
- NFR-4 外観: ライトモード固定・既存テーマ(`TekTheme`)に準拠。フォグの濃さは現行(黒 55%)と同等。
- NFR-5 検証可能性: 「晴れが地理座標に対して正しい位置・大きさで描かれる」ことを、実機目視に加えて自動テストで検証できる構造にする。
- NFR-6 互換性: Core Data スキーマを変更しない(マイグレーション不要)。対応 OS は iOS 18 以上、iPhone 専用のまま。
- NFR-7 本来機能への非干渉: 自動記録の検出・開始・停止・GPS・バックグラウンド維持の挙動を変えない。再構築は起動処理と監視開始をブロックしない。
  再構築中に確定した外出は、探索グリッドへの反映と目的分類が再構築の完了まで遅れてよい(記録そのものと保存完了通知は遅れない)。

## 5. 対象外

- 現在地(青い点)の表示追加
- フォグの色・デザインの刷新、セルサイズ(75m)の変更
- 開拓率の算出ロジックの変更(グリッド修正による値の是正を除く)
- 記録中の軌跡を探索マップへリアルタイム表示すること
- 外出削除を開拓済みセルへ反映すること
- iPad 対応、ダークモード対応
- バージョン番号の更新・App Store 提出

## 6. 制約・前提

- iOS 18 の SwiftUI `Map` はカスタム描画オーバーレイを提供しない。
- 開発機(Intel Mac)のシミュレータは MapKit の陸地を赤一色で描画する既知の不具合があり、地図面の目視確認は実機(iPhone XR)でのみ行える。
- 過去の外出の経路(`RoutePoint`)は端末内に保存されており、再構築の入力として使える。経路点が0件の外出は開拓に寄与しない。
- グリッドを変更するため、再構築後の「新エリア数」「開拓率」は更新前と異なる値になる。増減は経路の向きによる(平均では減少)。
- 再構築は現存する外出だけを入力にする。**削除済みの外出だけが開拓していた場所は、再構築でフォグに戻る**
  (通常時は FR-6.8 のとおり削除してもセルは残るが、今回の再構築に限り失われる)。
- 利用範囲は日本国内の徒歩・ランニング・自転車を想定する。経度 180 度付近や極域では、クラッシュしないこと以外は保証しない。
