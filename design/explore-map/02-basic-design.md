# 探索マップ作り直し + カレンダータブ移動 — 基本設計書

- 作成日: 2026-09-30
- 前提: `01-requirements.md`(要件定義書)。本書は「どういう方式・構成で要件を満たすか」を定める。
  クラスのシグネチャやアルゴリズムの細部は `03-detailed-design.md`(詳細設計書)で定める。

## 1. 方式の決定

### 1.1 フォグの描画方式(FR-2〜FR-5)

| 案 | 内容 | 評価 |
|---|---|---|
| 1. 現行方式の改良 | SwiftUI `Canvas` を地図に重ね、`onMapCameraChange(frequency: .continuous)` で毎フレーム座標変換して再描画 | ✕ カメラ通知と描画が別フレームになり操作中に遅れる(FR-2.1 の「操作中もズレない」を保証できない)。回転・ピッチ時の変換も自前 |
| 2. SwiftUI `MapPolygon`(穴あきポリゴン) | 世界を覆うポリゴンに開拓済みセルを内側ポリゴンとして抜く | ✕ 重なり合う穴は描画規則上正しく抜けない(セルを和集合に結合する幾何処理が必要)。ぼかし(FR-3.3)も不可 |
| **3. `MKMapView` + カスタム `MKOverlayRenderer`** | 地図のオーバーレイとして、地図座標系でタイル単位に描画 | **○ 採用**。位置・縮尺・回転・ピッチへの追従を MapKit が保証する。ぼかしも自由に描ける |

**採用: 案3。** iOS 18 の SwiftUI `Map` はカスタム描画オーバーレイを持たないため、探索マップの地図部分だけ
`UIViewRepresentable` で `MKMapView` をラップする。ピル・シート・CTA など地図以外は SwiftUI のまま残す。

これにより原因 A・B・C は「画面座標に描く」こと自体をやめることで解消する。

オーバーレイの階層は**地名ラベルより上**(`.aboveLabels`)とする。現行のフォグは地名ごと覆っているので、見た目を変えない(NFR-4)。
自宅・フロンティアのマーカー(注釈)は MapKit の仕様で常にオーバーレイより手前に描かれる(FR-2.2)。

### 1.2 セルデータの供給方式(FR-5)

| 案 | 内容 | 評価 |
|---|---|---|
| 1. 表示範囲ごとに取得(現行) | カメラ変更のたびに Core Data から範囲取得 | ✕ 取得タイミングと再取得判定が不具合 B・D の温床。描画スレッドから Core Data は引けない |
| **2. 全件を一度にメモリへ** | タブ表示時に全セルを読み、不変の空間索引にして描画側へ渡す | **○ 採用**。1セル=座標2値(16バイト)。50,000件でも1MB未満 |

**採用: 案2。** 表示範囲に依存する取得ロジック(`refreshFogIfNeeded` / `overlapRatio`)は廃止する(原因 B・D 解消)。

### 1.3 広域表示の扱い(FR-4、NFR-1)

縮小すると 75m セルは1ピクセル未満になり、(a) 見えなくなる (b) 1タイルに数千〜数万セルが入り描画が重くなる。
対策として**詳細度レベル(LOD)**を設ける: セルを地図座標上の 2^k 倍の升目に集約した粗いレベルを事前計算し、
縮尺に応じて「升目がタイル上で 4pt 以上になる」最も細かいレベルを選んで描く。これで1タイル(256pt 四方)に入る点は
最悪でも約 64×64 = 4,096 個に抑えられる(NFR-1)。セルが 4pt 以上に描かれる縮尺(画面幅がおよそ 4〜8km 以下。タイル縮尺の段階によるので
実測で確定する。初期表示の約 3km はどちらの場合も含まれる)では集約せず、セル中心そのものを使う(位置・大きさとも正確)。

**集約レベルの晴れは、元のセルの晴れを必ず覆う大きさにする。** 升目の中心に代表点を置くと、元のセルは最大で升目の半対角
(一辺の 0.707 倍)だけ離れている。そこで集約レベルでは、完全に晴れる半径・外周の半径の両方に升目の半対角を足す
(完全に晴れる半径 = 半対角 + 75m、外周 = 半対角 + 150m)。こうすると:
- 元のセルの「完全に晴れる範囲」と「外周」は、集約後も必ず含まれる(歩いた場所がフォグに戻って見えることはない)。
  ただしぼかし部分の濃さは一致しない: 元は複数セルのぼかしが掛け合わさって薄くなるが、集約は1つの円で描くため、
  ぼかしの重なる外縁ではわずかに濃くなりうる(フォグ濃度の2割弱まで)。範囲は欠けないので許容する。
- 隣り合う升目の完全に晴れる範囲が必ず重なるので、連続した経路が点線状に途切れない。縮尺を変えてもつながったままになる。
- 広がる量は最大で升目の対角ぶん(タイル上 6〜11pt 未満)。集約が始まる広域表示(画面幅およそ 4〜8km 超)に限られ、拡大すれば実寸に戻る。
  要件 FR-3.1 の実寸からの逸脱だが、FR-4(広域表示での視認性優先)と同じ趣旨の、欠けない方向の誤差として許容する。

**縮尺の基準**: MapKit はオーバーレイを2の累乗の段階的な縮尺(`draw` に渡る `zoomScale`)でタイルに描き、実際の表示縮尺に合わせて
拡大・縮小して表示する。LOD の選択と晴れの最小半径(FR-4.1)は、この `draw` に渡る `zoomScale` を基準に判定する。
タイルが表示時に最大2倍まで縮小されうることを見込み、最小半径はタイル上で「要件の 4pt × 余裕係数」とする
(係数の初期値は 2。実装工程で実測して確定する)。実測項目:
- タイルの縮尺が実際の表示縮尺より細かい側(表示時に縮小)か粗い側(表示時に拡大)か、その比の範囲。
  細かい側なら係数 2 で画面上 4〜8pt、粗い側なら係数を 1 に下げられる(係数 2 のままだと画面上で最大 16pt になる)。
- 集約が始まる画面幅の実測値(タイル縮尺基準では約 7.7km。粗い側なら画面上では約 3.9km まで近づく)。
  初期表示(約 3km)が集約なし・実寸どおりであることを確認する。

### 1.4 グリッドの定義(FR-6)

| 案 | 内容 | 評価 |
|---|---|---|
| 1. 現行(点の緯度で経度幅を決める) | — | ✕ 原因 E |
| 2. 経度幅を全世界で固定 | 緯度によらず同じ度数幅 | △ 一意だが、緯度で東西の実寸が変わる(日本国内でも北海道と沖縄で約2割差) |
| **3. 緯度行ごとに経度幅を固定** | まず緯度でバケット(行)を決め、その**行の中心緯度**で経度幅を決める | **○ 採用**。一意かつ、どの緯度でもほぼ正方形(75m)を保てる。自宅非依存(FR-6.2) |
| 4. 地図タイル座標系(Web メルカトル)で升目を切る | — | △ 一意だが実寸が緯度で変わり、既存の「75m」「開拓率の面積計算」の前提が崩れる |

**採用: 案3。** 既存の Core Data スキーマ(`ExploredCell.latBucket/lonBucket/centerLatitude/centerLongitude`)をそのまま使える(NFR-6)。

### 1.5 既存データの移行(FR-6.3〜6.7)

グリッド定義が変わるため、旧グリッドで作られたセルは新グリッドと番号が対応しない。変換ではなく**再構築**する:
`ExploredCell` を全削除し、保存済みの全外出を古い順に再生してセルと「新エリア数」を作り直す。
端末内に経路(`RoutePoint`)が残っているため損失はない。

- グリッドの版数を UserDefaults に持ち、旧版のときだけ実行する。完了時に版数を書き込む(中断→次回やり直し、FR-6.6)。
- 既存の「探索機能導入前の外出を後追い分類する」バックフィルと同じサービス・同じ起動タイミング(画面を伴う起動)に統合し、
  確定済みの全外出を対象に、分類済みの外出は**新エリア数だけ**更新、未分類の外出は従来どおり分類も行う(FR-6.3, 6.5)。
- セルの読み書きは従来どおり `ExplorationService` の単一 context で直列化する(セルの重複防止)。
- **外出単位の排他(FR-6.7)**: 「再構築の全体」と「外出1件の確定後処理(経路取得→分類→セル反映→新エリア数保存)」を
  同じ排他ゲートで直列化する。再構築中に確定した外出は、再構築が終わってから(=古い外出がすべて反映された状態で)処理される。
  再構築より前に確定済みだった外出は、再構築の対象一覧に入って古い順に再計算される。どちらの順でも結果は
  「古い順に1回ずつ反映」と一致する。成立に必要な規約:
  - **二重処理の無害化**: 外出の保存(`endedAt`)はゲートの外で行われるため、保存直後に再構築がゲートを取ると、その外出は
    再構築で処理された後、自分の確定後処理がもう一度走る。確定後処理はゲート取得後の最初に「処理済み(`classifiedAt != nil`)なら
    何もしない」を判定する。加えて、分類と新エリア数の保存は既存の `classifiedAt` ガード(未分類のときだけ書く)を維持する。
    再構築が分類済みの外出に使う「新エリア数のみ更新」は、再構築(ゲート保持中)からしか呼ばない。
  - **再入の回避**: 排他ゲートは再入不可。確定後処理は「ゲートを取る入口」と「ゲートを取らない本体」に分け、
    再構築(ゲート保持中)は本体だけを呼ぶ。
  - **版数の確認はゲート取得後**に行う(起動処理が重ねて呼ばれても再構築は1回だけ)。
  - **失敗時は版数を進めない**: セル全削除・各外出の反映・保存のいずれかが失敗したら、版数を書かずに終了し、次回起動で最初からやり直す
    (FR-6.6)。再構築中に削除された外出は失敗ではなく読み飛ばす。
- **進行状況の公開(FR-6.9)**: 再構築中かどうかを「現在値を保持する単一の状態」として公開する(購読した時点で現在値が届く)。
  フラグの読み取りと変更通知の購読を別々に行うと、その間に完了した場合に取りこぼすため、1つにまとめる。
  探索マップはこの状態を購読し、再構築中は「更新中」表示を出し、完了へ変わった時点で再読込する。

### 1.6 フロンティア候補と晴れの整合(FR-7.3)

フロンティア(未開拓方向)は従来「その地点のセルが未開拓か」だけで判定していた。晴れの半径(150m)はセル(75m)より広いので、
このままでは晴れて見える場所に「未踏エリア」マーカーが立つ。判定を「その地点から 150m 以内に開拓済みセルの中心が無いこと」に改める。
レイキャストの方位数・刻み・最大半径は変更しない。開拓率はセル単位のまま変更しない(FR-7.2)。

## 4. 主要な処理の流れ

### 4.1 探索マップの表示
0. 読み込みの契機は3つ: (a) タブ表示 (b) アプリがフォアグラウンドへ戻ったとき(探索マップ表示中の場合。地図の表示位置は保つ)
   (c) 再構築の完了。常駐アプリでタブ選択も残るため、(b) が無いと「探索マップを開いたまま歩いて戻ってきた」場合に反映されない(FR-8.1)。
1. `ExplorationService.fetchAllCells()` を呼ぶ(バックグラウンド context)。
   DEBUG 限定の起動引数 `-demoFogCells N` があるときは、取得結果に合成セル N 個をメモリ上で加える(Core Data には書かない)。
2. 結果から `FogCellIndex` をメインスレッド外で構築する。
3. `ExploreFogMap` に渡す → `FogOverlay` の索引を差し替え → レンダラに再描画を要求。
4. MapKit が必要なタイルごとに(バックグラウンドスレッドで)レンダラを呼ぶ → `FogPainter` が
   「フォグで塗る → 該当セルを晴らす」を地図座標で描く。
5. 以後のパン・ズーム・回転・ピッチは MapKit がタイルを変換・再要求するだけで、アプリ側のコードは走らない(FR-2.1)。

### 4.2 外出の確定
`SessionCoordinator.finalize`: 外出の保存(既存どおり)→ **保存完了通知**(順序を前へ移動)→ `OutingPostProcessor` の入口:
排他ゲート取得 → **処理済み(`classifiedAt != nil`)なら何もせず解放** → 経路取得 → 分類 →
`ExplorationService.recordVisited`(新グリッド)→ 新エリア数と分類を保存(`classifiedAt` ガード付き)→ ゲート解放。
探索マップは 4.1 の契機(次のタブ表示またはフォアグラウンド復帰)で反映する(FR-8.1)。

### 4.3 起動時の再構築
1. 起動時の `.task`(既存のバックフィル起動箇所。画面を伴う起動でのみ走る)で `ExplorationBackfillService.runIfNeeded()`。
2. グリッド版数が旧版 → 排他ゲート取得 → **版数を再確認**(待っている間に完了していたら何もしない)→ 状態を「再構築中」に →
   セル全削除 → 確定済みの全外出を列挙 → 古い順に1件ずつ(`OutingPostProcessor` の本体。ゲートは取らない):
   経路取得 → `recordVisited` → 分類済みなら新エリア数のみ更新/未分類なら分類して保存。
3. 全件成功で版数を保存 → 状態を「完了」に → ゲート解放。以降の起動では 2 をスキップする。
   途中で失敗した場合は版数を保存せずに状態を戻してゲートを解放し、次回起動で最初からやり直す。
4. 版数が最新なら、従来の未分類バックフィル(1件ごとに `OutingPostProcessor` の入口を通る)を行う。
5. 探索マップは再構築状態を購読する(購読時点の現在値が届くので、タブ表示時点で既に再構築中でも取りこぼさない)。
   再構築中は更新中表示を出し、完了へ変わったら 4.1 をやり直す(FR-6.9)。

ヘッドレス再起動(位置イベントによる画面なしの起動)では `.task` が走らないため再構築しない。その間に確定した外出は
4.2 のとおり新グリッドでセルを記録し、次に画面を開いた起動の再構築で全体が作り直される(FR-6.3)。

## 5. 並行性の設計(NFR-3)

| 対象 | 実行コンテキスト | 方針 |
|---|---|---|
| `MKMapView` / `ExploreFogMap` / 注釈 | MainActor | UIKit 規約どおり |
| `FogOverlayRenderer.draw` | MapKit のバックグラウンドスレッド(複数同時) | 参照するのは不変の `FogCellIndex` スナップショットのみ。ロックで取り出して以後はロック外で描画 |
| `FogCellIndex` の構築 | MainActor 外(detached) | 値型・`Sendable`。構築後は変更しない |
| `ExplorationService` | 自身の単一 background context の `perform` | 既存方針を維持。全削除・全件取得も同じ context を通す |
| 再構築 | 起動 `.task` から独立 `Task` | 起動・監視開始をブロックしない(NFR-7) |

| `OutingPostProcessor`(入口) | `SessionCoordinator.finalize` の Task(既存の独立 Task)内 | ゲート待ちで遅れるのは探索グリッドへの反映と分類だけ(保存完了通知はゲートの前に出す)。検出・次の外出の開始は `finalize` を待たない(既存構造) |

## 7. リスクと対応

| リスク | 対応 |
|---|---|
| タイル描画での「抜き」(destinationOut 合成)が実機で期待どおりにならない | 単体テストでオフスクリーン描画を検証。実機で目視確認。不可なら「晴れ領域をクリップから除外して塗る」方式へ `FogPainter` 内部だけ差し替え可能な構造にしておく |
| この開発機のシミュレータでは地図面を目視できない | 描画ロジックを `FogPainter` に分離して自動テスト。最終確認は実機 |
| 再構築で「新エリア数」「開拓率」が変わる。削除済み外出だけが開拓した場所はフォグに戻る | 仕様として要件 §6 に明記済み |
| 再構築が長引く(探索機能導入前の版からの更新では、未分類の外出ごとに店舗検索の通信が入る)と、その間に確定した外出の探索グリッドへの反映と分類が遅れる | 記録と保存完了通知は遅れない(通知はゲートの前に出す)。再構築は1回限り |
| タイルの縮尺(2の累乗の段階値)と実際の表示縮尺が最大2倍ずれ、画面上の最小半径が要件の 4pt を下回る | 判定は `draw` に渡る縮尺を基準とし、余裕係数(初期値 2)を掛ける。実装工程で表示倍率の範囲を実測して係数を確定する(§1.3) |
| 特定の外出の反映が毎回失敗すると、再構築が完了せず起動のたびにやり直しになる | 削除済みの外出は失敗扱いにせず読み飛ばす。それ以外の失敗(ストア障害など)は版数を進めないことを優先する(誤った状態を固定しない) |
| 1タイルに点が集中すると描画が重い | LOD で上限を約 4,096 点に抑え、自動テストで計測。閾値を超える場合は晴れの描画を「事前に作ったグラデーション画像の貼り付け」に切り替える(`FogPainter` 内部のみの変更) |
| 経度 180 度をまたぐ表示・極域 | 利用範囲外(日本国内の徒歩・自転車)。クラッシュしないことのみ保証 |
